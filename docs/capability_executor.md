# Capability Executor Boundary

The runtime uses official LLM tool-calling only at the model boundary. Internally,
all provider-specific tool calls are adapted into `CapabilityRequest` and are
executed through `CapabilityExecutor`.

## Boundary

```text
Official LLM tool call / local JSON / plugin event
    -> adapter
    -> CapabilityRequest
    -> CapabilityExecutor
    -> Supervisor / TaskStore / SQLiteVecStore / HookStore / CodexTaskWorker
    -> CapabilityResult
    -> adapter result message if the caller is an LLM
```

This prevents provider-specific tool-call formats from leaking into core
runtime code.

## First-class internal capabilities

- `task_state`: read task state.
- `task_tail`: read task stdout/stderr tail without interrupting it.
- `task_history`: read state, output, events, and summaries.
- `memory_search`: vector-first memory search.
- `hook_schedule`: deterministic runtime wakeups/hooks.
- `interrupt_request`: orderly pause/resume/stop/cancel request.
- `spawn_task`: create bounded managed tasks; heavy execution remains delegated
  to task backends such as Codex CLI.

## Rules

1. Do not expose raw shell/file/process primitives as main-agent capabilities.
2. Heavy code/file/project work goes through task backends, currently `codex-cli`.
3. `CapabilityExecutor` is the single runtime entry for capability execution,
   regardless of whether the caller is main, interactive, audit, automation, UI,
   or plugin.
4. Official LLM tool schemas are generated by boundary adapters such as
   `OpenAIToolAdapter`; they are not the internal runtime API.
5. Risky capabilities should be audited or routed through supervisor policy.

## Role permissions

The first-pass policy is deny-by-default except for explicit role capability sets:

- `main`: task read, memory search, hook schedule, interrupt request, spawn task.
- `interactive`: low-latency task read only.
- `audit`: read paths plus interrupt request.
- `memory`: memory search and hook schedule.
- `task`: task read paths.
- `supervisor`: all capabilities.

Medium/high-risk calls are still routed through runtime policy. `spawn_task` is
reviewed by `Supervisor`/`AuditAgent`; `interrupt_request` and plugin hook
scheduling are audited by `CapabilityExecutor` before execution.
